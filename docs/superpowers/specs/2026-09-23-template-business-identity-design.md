# 模板业务唯一标识与模糊匹配设计

## 目标

省公司模板不再以业务编号作为唯一身份。第一批、第二批以及后续批次允许重复使用 `01`、`02` 等展示编号，程序必须依据业务名称别名识别唯一业务，再选择该业务下的模板变体。

成功标准：

- 第一批 `01 营销售电` 与第二批 `01 股权（产权）管理` 不会互相选择模板。
- `03 电网基建` 可在同一业务下选择 `35-220kv`、`500-750kv` 两个变体。
- `28` 至 `31` 等编号不受原有 `01` 至 `10` 限制。
- 零匹配和多匹配时停止模板写入并给出可定位的错误，不按编号猜测。
- 模板文件继续使用 SHA-256 校验，文件缺失或内容变化时终止运行。

## 配置模型

使用 JSON 配置。每个业务具有全局唯一的 `business_id`，`business_code` 仅用于展示。模板放在 `variants` 数组中，普通业务也使用一个 `default` 变体，保持结构统一。

```json
{
  "schema_version": "2.0",
  "businesses": [
    {
      "business_id": "equity_management",
      "business_code": "01",
      "business_name": "股权（产权）管理",
      "aliases": [
        "股权（产权）管理",
        "股权产权管理",
        "股权管理"
      ],
      "variants": [
        {
          "variant_id": "default",
          "aliases": [],
          "template": {
            "path": "审核/第二批风控矩阵及“三清单”（省公司版）/01 股权（产权）管理-省公司版/01风控矩阵-股权（产权）管理（省公司版）.xlsx",
            "sha256": "实际文件哈希"
          }
        }
      ]
    }
  ]
}
```

约束：

- `business_id` 在整个配置中唯一且不可为空。
- 同一业务内 `variant_id` 唯一。
- `aliases` 去除空白后不可为空，不允许只配置纯数字编号。
- 每个变体必须有唯一模板路径和 SHA-256。
- 不兼容旧版仅含 `entries` 的基准配置；发布新规则包时一次性迁移。

## 匹配规则

### 输入文本

使用报送文件相对于输入根目录的完整路径，包括所有上级目录和文件名。业务匹配不读取工作簿正文。

### 规范化

业务路径和别名统一执行：

1. Unicode NFKC 规范化。
2. 英文字母转小写。
3. 删除空白字符。
4. 将中文括号、英文括号、连接号等常见分隔符归一化或移除。

编号不参与业务选择。

### 业务选择

当规范化路径包含某条规范化业务别名时，该业务成为候选项。

- 无候选：报告“未找到业务模板映射”。
- 只有一个候选业务：选择该业务。
- 多个候选：优先使用命中的最长别名；最长别名仍并列时报告“业务模板映射冲突”。

不得使用编辑距离、向量相似度或语义模型自动猜测业务。

### 变体选择

在已选业务内部匹配 `variants[].aliases`：

- 命中唯一非默认变体：选择该变体。
- 未命中非默认变体，且业务仅有一个 `default` 变体：选择 `default`。
- 多个非默认变体同时命中：报告“模板变体映射冲突”。
- 业务包含多个非默认变体但路径未命中任何变体：报告“模板变体无法确定”。

### 模板加载

模板按配置中的固定路径加载并校验 SHA-256。加载结果以 `(business_id, variant_id)` 为键保存。报送文件也保存 `business_id`；后续基准选择、审核上下文和“省公司版本责任主体（核对后删除）”列都使用该键。

模板行内责任主体仍按控制点序号和控制措施序号匹配，但匹配范围必须先限定在相同 `business_id` 和 `variant_id` 内。

## 数据流

```text
报送相对路径
→ 规范化
→ 业务 aliases 模糊包含匹配
→ 唯一 business_id
→ 变体 aliases 匹配
→ 唯一 variant_id
→ 从 JSON 读取模板固定路径和哈希
→ 加载模板
→ 写入省公司版本责任主体核对列
```

## 错误处理

以下情况不得继续写入模板责任主体：

- 业务未匹配。
- 业务匹配冲突。
- 变体未匹配或冲突。
- 模板文件不存在。
- 模板哈希变化。
- 模板解析失败。

错误信息必须包含报送相对路径、候选业务或变体、命中的别名以及建议补充的配置位置。

## 迁移范围

1. 将现有第一批 11 份模板迁移到新 JSON。
2. 加入第二批 8 份模板。
3. 为第一批与第二批重复编号业务分别分配不同 `business_id`。
4. 扩展文件记录、审核范围和基准索引，使其携带 `business_id`。
5. 删除仅支持 `01` 至 `10` 的业务编号识别限制；编号保留为展示字段。
6. 更新当前发布规则包并发布新版本，不原地修改历史发布包。

## 测试要求

- 第一批 `01 营销售电` 正确选择第一批模板。
- 第二批 `01 股权（产权）管理` 正确选择第二批模板。
- `02`、`03`、`08` 重号业务分别选择正确模板。
- `28` 至 `31` 正确识别。
- 路径中的空格、全角括号、半角括号和大小写差异不影响匹配。
- 最长别名可以消除包含关系歧义。
- 同长度多业务命中时拒绝猜测。
- 电网基建两个电压变体正确选择。
- 模板缺失、哈希变化、零匹配和多匹配均有明确错误。
- 审核输出中的“省公司版本责任主体（核对后删除）”来源于正确模板。
