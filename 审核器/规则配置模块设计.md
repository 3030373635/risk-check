# 规则配置模块及关联模块适配设计

本文现对应程序及规则包1.5.0，包含v2规则与后续已确认口径。实际命令及执行边界以[运行说明](README.md)、已发布规则包及[语义辅助说明](本地语义辅助运行说明.md)为准。1.3.0的技术限制分流政策继续保留。

目标是将审核口径从程序判断分支中分离，使用户能够新增和调整规则，并让解析、关联、执行、意见回填及验证模块随规则变化工作。审核运行全部在本地完成；小型文本向量模型只检索候选，不理解或执行用户输入的自然语言规则，不调用生成式大模型。

1.5.0增加`semantic_config.version=2`：限定适用性及责任主体领域，分别配置岗位、部门、适用表达的候选最低分和歧义分差；`candidate_only`必须为true，不能设置自动通过。R05覆盖能力版本6只替换候选检索，不改变覆盖判断。旧版本能力保留；禁止为新包重新启用载体语义领域。重复关系分组保留各措施来源，不产生跨措施授权。

## 一 配置能力及其边界

用户通过选择检查类型、选择字段、填写参数和适用范围来定义规则。规则名称和说明用于阅读，不直接作为可执行逻辑。

| 用户变化 | 配置模块如何处理 | 是否需要开发 |
| --- | --- | --- |
| 开启或暂停一项规则 | 调整启用状态，发布新规则包 | 否，前提是检查能力已实现 |
| 调整适用业务、主体或例外 | 修改范围、主体代码及排除条件 | 否 |
| 更改必填项、禁用词、角色关系、阈值 | 修改相应检查类型的参数 | 否 |
| 修改审核意见措辞 | 修改受约束的意见模板并预览 | 否 |
| 新增使用已有检查类型的规则 | 新建稳定规则ID，选检查类型、字段、参数和输出位置 | 否 |
| 给旧规则增加一个检查点 | 在规则下新增独立检查ID | 否，前提是所需字段及检查类型已支持 |
| 新增Excel列的别名 | 将新表头映射到已有逻辑字段 | 否，需通过映射校验 |
| 引入新的结构化字段 | 在字段目录登记类型、读取位置和规范化方法 | 简单直接列读取可配置；新的提取方式需开发适配器 |
| 增加全新的判断逻辑或数据来源 | 扩展检查器或读取适配器，登记能力及回归用例 | 是，但不应改写其他无关规则 |
| 要求判断自由文本的深层业务含义 | 明确可验证的条件，或保留人工复核 | 不能仅靠填写一段规则文字实现 |

“任意新需求都无需代码”不作为目标。首版应做到已有能力可组合、新能力有明确扩展接口，且修改一条规则不需要在多个模块中重复修改同一口径。

## 二 模块边界和数据流

```text
规则维护入口
    │ 选择检查类型、编辑参数、范围和意见
    ▼
规则配置中心
    ├─ 字段与检查能力目录
    ├─ 规则定义、字典、模板映射及基准引用
    ├─ 配置合并、校验、差异预览
    └─ 版本发布、冻结与回滚
    │
    ▼
不可变运行快照 → 输入与字段需求计划 → 解析和事实准备
                                          │
                                          ▼
                              通用规则执行器调用检查器
                                          │
                                          ▼
                              标准问题对象 → 意见写回

验证模块分别比较：配置差异、问题差异、人工标注命中差异。首版命令行以 `config-diff` 比较规则包，并以离线确定性的 `run-diff <前次运行目录或findings.json> <后次运行目录或findings.json>` 按 `finding_key` 输出问题新增、移除、措辞变化和状态变化；同一输入可复现排序一致的结果。
```

配置中心负责确定“查什么、对谁查、用什么参数、如何表达意见”。检查器负责完成一种有明确定义的代码计算。执行器负责范围判断、输入状态、调用和记录，不再通过`if rule_id == 'R08'`等分支决定业务例外。

## 三 规则包与规则定义

### 1 一次运行绑定一个完整规则包

规则包包含规则定义、字段目录、表头别名、主体别名、岗位及载体字典、基准清单和适用范围配置。发布时冻结全部资源的内容或哈希，不能只给规则JSON打版本而继续读取会变化的外部字典。

运行快照记录规则包版本、引擎版本、检查器版本、完整有效配置、输入哈希及明确的审核时点。生效日期根据本次审核时点计算，不能简单使用电脑当前日期决定历史材料适用哪版规则。

原有R01至R12作为本期规则包的初始规则，不是引擎允许的最大数量。执行器遍历规则包，新增第13项或将第5项拆分为更多检查点均不依赖固定长度数组。

### 2 规则字段契约

| 字段 | 定义 |
| --- | --- |
| `rule_id` | 永久稳定的机器标识，例如`duty.separation`，不使用Excel行号作为标识 |
| `display_code` | 面向审核人员的编号，例如R08，可随文档编排调整 |
| `title`、`source_reference` | 规则名称和审核依据；新增规则说明其业务来源 |
| `revision` | 同一规则的修订号，参数、范围或文案变化均形成修订 |
| `enabled` | 是否启用；关闭仍保留定义和停用原因 |
| `scope` | 记录类型、业务编号、变体、会计主体代码、审核批次等适用范围 |
| `checks` | 规则下的独立检查项，每项具有稳定`check_id` |
| `operator`、`operator_version` | 选用的已登记检查能力及版本 |
| `params` | 与检查类型对应的有类型参数；字段名采用逻辑字段ID |
| `on_unavailable` | 配置业务差异无法确定时的处理。1.3.0先由结果政策分流技术限制与前置依赖为内部limitation，不生成单位待核实 |
| `message` | 检查器失败或资料不足时的意见模板；只允许引用登记的证据变量 |
| `location_policy` | 明细行、关联两侧或资料级位置，从预设策略中选择 |

必填字段检查中的“字段值为空”属于应发现的问题，不能因为缺少值就提前跳过该检查。应区分字段完全未被模板识别、单元格值为空、公式无可用缓存、关联对象不确定等状态。

`checks`采用独立发出问题的方式，一条规则可以同时发现部门、岗位和姓名问题。需要组合条件时使用检查器登记的结构化`all`、`any`或过滤参数；缺少数据时保持“未知”，不能将未知自动算作真或假。首版不提供可执行Python、`eval`、任意SQL或动态下载脚本的配置入口。

### 3 原子检查示例

以下为当前第8条配置，包含员工报账。`roles_same_duty`固定按主体、业务、变体及措施编号隔离，再核对职责和人员；不能通过配置删除隔离条件。

```json
{
  "checks": [
    {
      "check_id": "handler_reviewer_overlap",
      "location_policy": "related_rows",
      "message": {
        "review": "{advice_v2}（第8条）",
        "violation": "{advice_v2}（第8条）"
      },
      "on_unavailable": "review",
      "operator": "roles_same_duty",
      "operator_version": 1,
      "params": {}
    }
  ],
  "display_code": "R08",
  "enabled": true,
  "revision": 3,
  "rule_id": "duties.separation",
  "schema_version": "1.0",
  "scope": {
    "business_codes": {
      "exclude": [],
      "include": [
        "*"
      ]
    },
    "entity_codes": {
      "exclude": [],
      "include": [
        "*"
      ]
    },
    "record_type": "position_duty"
  },
  "source_reference": "v2第8条：含员工报账，仅职责内容相同且经办审核人员重合时提示冲突",
  "title": "经办审核人员分离"
}
```

`person_keys`不是简单姓名字符串集合。事实准备层保留人员编号、姓名及身份可靠性；只有姓名重合且不能排除同名时，检查器返回待核实，不能套用“已确认重合”的意见。

新增规则的流程同样是新增定义。例如今后要求检查完全重复的岗位记录，可复用`records_unique`能力。下面仅演示扩展，默认关闭，未纳入本期有效规则：

```json
{
  "schema_version": "1.0",
  "rule_id": "example.duplicate_position_record",
  "display_code": "EX01",
  "title": "示例新增规则 重复岗位记录",
  "source_reference": "扩展示例 未纳入本期审核口径",
  "revision": 1,
  "enabled": false,
  "scope": {
    "record_type": "position_duty",
    "business_codes": {"include": ["*"], "exclude": []},
    "entity_codes": {"include": ["*"], "exclude": []}
  },
  "checks": [
    {
      "check_id": "duplicate_row",
      "operator": "records_unique",
      "operator_version": 1,
      "params": {
        "key_fields": ["entity_code", "business_code", "variant_id", "measure_id", "department", "position", "person_keys", "role"]
      },
      "on_unavailable": "review",
      "message": {
        "violation": "【重复记录】本行与{duplicate_locations}的岗位记录完全重复，请核实。",
        "review": "【重复记录】待核实：{unavailable_reason}。"
      },
      "location_policy": "related_rows"
    }
  ]
}
```

集合类型字段在比较前按登记的规范化方式处理，例如人员集合排序后比较；人员身份不明不能作为确定重复的依据。规则删除后保留退役标识，不把旧`rule_id`或`check_id`分配给另一种含义。

## 四 检查能力目录与字段目录

### 1 检查能力目录

| 检查类型 | 可配置参数示例 | 对应业务 |
| --- | --- | --- |
| `required_documents` | 材料类别、扩展名、应报范围来源 | R01、R02 |
| `required_fields` | 字段、占位值、条件性必填 | R03、R05 |
| `schema_contains` | 基准字段集合、允许别名、忽略的历史字段 | R03 |
| `forbidden_reference` | 禁用系统或字典、目标字段、控制点范围 | R04当前停用，保留历史能力 |
| `coverage` | 原泛称映射检查 | 仅供历史规则包使用 |
| `responsibility_coverage` | 同措施关联、分列部门岗位组合优先匹配、已确认映射和别名 | 当前R05；unresolved_kind=review，未确认映射写待核实；历史默认limitation |
| `applicability_values` | 适用情况、合并字段内原因或对应备注、占位符 | 当前R03；按实际填写值检查 |
| `sheet_exists` | 清单类型、可接受工作表或明确区域 | R06 |
| `roles_disjoint` | 分组字段、角色对、人员身份字段 | 历史R08 |
| `roles_same_duty` | 固定同主体、业务、变体、措施范围，比较职责与身份 | 当前R08 |
| `field_constraints` | 字段、占位词、占位模式及岗位分隔符 | 当前R05 |
| `reference_exists` | 当前表与目标表、同主体关联键 | 当前R09 |
| `set_subset` | 历史载体引用集合核验能力，供旧版本复现 | 当前规则包不调用 |
| `deleted_text_reappears` | 矩阵来源字段、职责目标字段、匹配范围；删除片段及原单元格位置 | 当前R13：仅相同措施编号，删除原文不设字数门槛 |
| `text_pattern` | 句式及匹配方式 | 历史R10 |
| `responsibility_phrase` | 可接受责任属性集合 | 当前R10；同时要求对象和承担责任表达 |
| `value_mapping` | 经办与主体责任等映射 | R11 |
| `ordered_records` | 基准顺序、自然排序、分组连续性 | R12 |
| `records_unique` | 唯一性字段、空值和身份不确定处理 | 后续扩展示例 |

每种能力登记参数结构、支持的数据类型、所需字段或事实、可返回的证据变量、适用记录类型、输出位置能力和边界用例。系统启动时从本地代码注册表加载，业务用户只选择已实现的能力。暂停的R07不要求已有完整实现，但重新开启时必须先检查能力和参数是否齐备，不能把开关打开就显示为可执行。

### 2 字段目录

1.3.0新增`result_policy.json`，固定契约为`{"version":1,"technical_issues":"internal","unfinished_is_pass":false}`，校验拒绝其他政策，随规则包冻结并计入哈希。引擎依据问题类型及前置字段状态分流，再渲染单位意见；不是按意见文本删除记录。内部记录包含`cause_type`、`root_cause_id`、`blocked_by`，按需附`field_source`和`baseline_relation`，集中事项保留`affected_locations`及完整原记录。导出器拒绝内部记录写入单位意见。

1.3.0使用`set_subset@4`、`responsibility_coverage@4`、`responsibility_phrase@4`、`ordered_records@2`。基准快照增加同措施当前载体与措施文字；共同模板差异保持未完成，不作为允许载体白名单。读取恢复与业务判断分别验收，旧能力和冻结规则包保留，复现旧结果需使用相应代码快照。

历史1.4.0在此基础上使用`set_subset@5`、`responsibility_coverage@5`及`applicability_values@2`，新增三项随规则包冻结的资源：

| 资源 | 作用和限制 |
| --- | --- |
| `parser_policy.json` | 限定主体代码的表头简称；同一简称不自动推广到其他主体 |
| `semantic_lexicon.json` | 明确文字模式、适用性类别原型和候选关系；模板采用、暂无业务不直接生成适用性结论 |
| `semantic_config.json` | 本地模型路径、清单哈希、CPU线程及缓存配置；当前校验要求`candidate_only=true` |

1.4.1从R09的执行检查数组中移除`carrier_subset`，不会调用`set_subset`，也不会生成载体解析、模板差异和语义候选任务。R09独立的`measure_exists`保留；R13不依赖被移除的子项。历史能力和不可变旧规则包保留用于复现。

模型仅为同范围的待核实表达寻找候选。排序分数不是通过条件，候选不自动写入已确认别名。岗位编号如出现相同业务前缀、环节序号及措施序号而名称不同，指出具体编号差异，不强行合并，不认定岗位记录必然缺失；第9条、第13条的原编号关联不受此提示影响。模型缺失、缓存损坏及超长输入均保留运行证据，不联网补资源。

规则使用`department`、`position`、`person_names`、`measure_id`等逻辑字段，不直接引用H列或第3行。字段目录登记类型、允许空值、适用表类型、读取方法、规范化方法和原始坐标。

新增“员工姓名”作为`person_names`的别名，仅更新字段映射；新增“任岗起始日期”等新字段，需要登记日期类型及直接列读取方法。涉及从复杂文本推断日期范围的新要求，需增加提取适配器后才能启用相应规则。

1.2.11补充：`input_overrides.json`为可选列确认资源，内容为数组，每项必须有 `file_path`、`sha256`、`sheet`、`field`、`column`、`reason`。字段须属于本表业务字段，列号为1—16384，同文件/表/字段不得重复配置。源文件哈希变化时停止套用，禁止将人工审核意见列映射为业务数据。资源随规则包冻结并纳入快照，不凭内容相似度自动生成确认项；初始发布为空数组。

隐藏列选择为读取器统一政策：等价字段优先可见列，唯一隐藏字段照常读取。单位限定不因映射成同一字段而丢弃；多个可见列相互冲突时，只有明确的本单位归属、成组对应或完整内容等价证据才能选择。业务规则继续读取选定字段，原值为空与字段未识别分别报告。

新增版本能力包括 `schema_contains@2`、`required_documents@2`、`responsibility_coverage@3`、`roles_same_duty@2`、`set_subset@3`、`responsibility_phrase@3`。旧能力保留，1.2.11规则包要求程序至少1.2.11；基准、原规则版本及人工结果不改写。第9条的载体简称关系仅由同措施明确的完整载体名称结构派生，不用于第13条删除原文比对。

原始记录保存可扩展的`attributes`及`provenance`，保留未映射的非审核业务单元格，以便后来新增字段时重新映射。历史人工审核列、批注和标签在记录层隔离，不进入可被规则选择的业务字段目录。

## 五 配置组合 校验及生效方式

### 1 配置组合

按“本批次默认规则包—明确的业务变体配置—明确的主体配置”形成有效配置。主体覆盖只能引用标准主体代码，不能用未经确认的简称决定例外。岗位、载体、字段等字典作为规则包资源统一解析。

覆盖操作采用指定字段路径替换：未提供的值继承，数组整体替换，不隐式拼接；`null`仅在字段定义允许时有效。相同优先级在相同适用范围对同一参数给出不同值时，校验报错，不能根据文件读取顺序选择一个。

例外配置不得隐式扩大本批次应报主体或业务范围。需要增加审核业务时，明确修改批次范围，再调整相应规则。`include: ["*"]`表示当前批次范围内全部对象；空的`include`视为配置错误，避免将填写遗漏解释为全查或全不查。

### 2 两层校验

发布前检查配置结构、未知字段、字段类型、规则及检查ID重复、版本兼容、检查能力是否存在、参数范围、意见模板变量、字典引用、覆盖冲突和事实依赖是否成环。意见模板使用有限占位符替换，不执行表达式。

运行前检查所需工作表、字段和适配能力是否具备。错误的配置停止该版本运行，不生成新的正式审核副本；正确配置遇到缺少资料，则按规则产生待核实问题，并继续不依赖缺失资料的检查。

新字段缺失不能静默跳过启用规则。缺编号的业务行仍进入必填检查，不能先用“有编号才是记录”的条件过滤掉。每个检查记录执行、范围排除、配置停用、部分完成或执行失败，不能统一显示为通过。内部limitation对象不进入findings.json及审核意见列；执行器将其定位与原因写入limitations.json，并在CheckStatus.limitations中计数。存在限制时状态为partial。summary中的write_completed仅表示副本写入完成，has_check_limits标识尚有未完成的核对。

### 3 用户维护流程

```text
复制当前版本形成草稿
    → 编辑规则、范围、参数或意见
    → 校验配置与能力
    → 在指定样本上试运行
    → 查看新增、消失、变化及未执行的检查
    → 发布新版本
    → 新任务使用该版本
```

首版以结构化JSON及命令行完成同一套校验、试运行和发布接口。便于业务人员使用的后续入口，可提供规则列表、单规则表单、适用范围选择、检查类型参数表、意见预览、版本差异和回滚操作；表单根据能力目录生成，新增已登记检查类型无需重新写整套页面逻辑。

启用版本只影响新任务。运行中的审核固定使用启动时的快照，不在处理中途热更新。回滚是选择已冻结的旧版本重新运行，不修改已发布版本内容或历史输出。

## 六 其他模块必须同步调整

| 模块 | 需要的适配 | 目的 |
| --- | --- | --- |
| 文件扫描与主体归集 | 从快照读取材料类型、别名和范围，记录资源版本 | 公司名称和应报范围调整后不改扫描代码 |
| 表头与读取适配 | 读取字段目录和映射，暴露字段存在、值空、缓存不可用等状态 | 新字段、新表头能被规则发现，避免误判通过 |
| 数据模型 | 核心身份字段稳定，业务字段可扩展，字段值附类型及坐标 | 新规则不强制频繁修改所有模型类 |
| 事实准备与跨表关联 | 根据启用检查的能力声明准备角色、身份、措施匹配、载体集合等事实 | 公共计算复用，且不依赖另一规则是否报错 |
| 规则执行器 | 动态遍历规则与检查，统一范围、未知状态及错误处理 | 增加规则无需加总调度分支 |
| 问题归并 | 按稳定规则ID和检查ID区分问题，保留依据及修订号 | 改编号、改措辞不破坏追溯，多个新检查不互相覆盖 |
| 意见写回 | 只接受标准问题对象及预设位置策略，不理解具体业务规则 | 新规则直接复用一列回填及格式保护 |
| 运行日志与缓存 | 按实际依赖的文件、规则、字典、映射及能力版本判定失效 | 不因只改字典而错误沿用旧结果 |
| 人工对照验证 | 标签关联稳定规则／检查ID，分别冻结人工原句和本期范围映射 | 调整规则后能说明差异，避免修改答案追求命中 |
| 维护入口 | 读写同一规则包及校验服务，展示有效配置来源 | 命令行与后续表单不各自实现一套口径 |

R08需要角色事实，不应依赖“R11审核通过”；R13删除原文检查需要主体、业务、模板类型及相同措施编号的关联信息，以及完整的删除线片段，不依赖旧版编号检查或载体别名字典。事实准备与出具审核意见必须分离。停用一个规则不应破坏另一个仍启用规则的基础数据。

对于跨表关系，主体代码、业务及变体隔离属于引擎基本约束，普通规则参数不能去掉这些边界形成跨主体比较。人工初审内容隔离、源文件不改写、只有问题才写审核列，也作为固定运行约束，不作为一般业务规则可关闭的选项。

## 七 调整规则后的结果和意见管理

新规则包发布前，对同一冻结样本执行前后版本，比较问题新增、消失、内容变化、适用范围变化及因资料不足不能执行的变化。用户应能够看到“只改措辞”与“改变判定条件”的不同影响。

问题保存两种标识：跨运行匹配用的`finding_key`由规则ID、检查ID、主体、业务、记录标识和问题类型组成；本次发生记录用`finding_id`并记录运行ID、规则修订及证据。条件含义变化时递增修订号，含义彻底替换时新建检查ID，保留旧ID退役记录。

首版采用完整重跑，并完整重建本次范围内的“审核意见”列。修改、停用、删除或缩小范围后，任何旧意见都不得残留成当前有效问题；程序意见归属清单仅记录本轮写入位置，不用于继承旧文字。

增量重跑作为后续优化。只有在字段、主体映射、关联关系和全表排序等依赖都能证明不变时，才复用旧结果。改主体别名会影响归集和跨表关系，改基准会影响字段与排序，改意见文案只影响呈现；不能只看规则文件是否变化来决定缓存有效。

## 八 本期规则如何迁移到新结构

1. R05拆成部门具体性、岗位具体性、姓名填写、职责填写、措施编号、责任覆盖等独立检查点，仍可统一展示“第5条”。调整姓名要求不会连带关闭部门检查。
2. R06使用清单存在性检查，参数允许空明细；第12条排序独立定义，不挂在R06之下。
3. R04、R07在本期包中关闭，停用原因明确记录；R12排序仍执行。
4. R08在本期包中包含员工报账。职责统一排版空白、全半角，仅将主体责任和审核责任的责任类型归一后比较；保留其他动作词及标点。
5. v2曾恢复R09的`reference_exists`与`set_subset`；1.4.1按最新确认移除`set_subset`，仅保留编号核对。R13独立启用`deleted_text_reappears`，检查相同控制措施编号下删除原文是否仍出现在有效岗位职责中。删除原文仅忽略排版空白，单字、短词和标点均不排除。
6. R10句式和责任属性放入参数，R11角色与责任映射放入版本化资源。配置变化后统一触发相关回归用例。
7. R03接受最后两列为适用性与原因/备注，字段齐全时拆分本身不产生意见；仅有备注栏名不能视为原因已填写。表内存在多处修改备注时，优先读取与本单位适用性栏相邻的原因栏。基准忽略的适用性等价字段不再按旧坐标报缺列，其他业务字段核对保持启用。
8. R01和R02的主体及文件范围配置与归集模块共用，避免审核层和扫描层分别维护不同的应报主体集合。

## 九 开发与验收补充

### 1 开发先后

在原P0阶段冻结规则包、字段契约及检查能力契约。P1建立配置加载、有效配置合并、静态校验和运行快照，再让解析层消费字段目录。P2开始将本期规则实现为检查器和规则定义；P3完善公共事实及跨表能力；P4实现版本化结果写回；P5验证规则变化后的效果和复现能力。

不能先把十二条写成固定判断，再在最后加一个配置文件作为外壳。配置必须从第一批规则实现开始成为实际参数来源。

### 2 拟议验收场景

| 场景 | 可验证结果 |
| --- | --- |
| 新增使用已有检查类型的演示规则 | 不改执行器和写回代码即可产生可定位的新问题 |
| 只修改R10允许责任属性 | 仅相关句式检查结果按配置变化，其他检查不受误影响 |
| 调整R08适用范围 | 员工报账适用范围以配置为准，其他角色检查继续运行 |
| 关闭R11 | R08仍可使用事实准备层提供的角色信息 |
| 修改表头别名或增加简单字段 | 解析正确变化；未识别字段明确报出，不静默跳过 |
| 引用未知检查器、错误参数或未登记模板变量 | 配置校验失败，指出规则、检查及字段位置 |
| 暂停的R07没有实现就被开启 | 启用校验明确失败，不能假装完成审核 |
| 相同优先级的主体或业务覆盖冲突 | 校验拒绝含糊版本，不按读取顺序覆盖 |
| 规则停用、退役、缩小范围或只改文案 | 新副本清空旧审核意见，只写本轮结果 |
| 一个审核正在运行时发布新版本 | 当前任务使用原快照，新任务使用新版本 |
| 回滚旧规则包 | 同输入、同引擎和同依赖版本复现旧问题集合 |
| 新增字段或检查尝试读取人工审核列 | 配置及字段访问拒绝，原有答案隔离测试仍通过 |

以上为实施阶段的验收标准。本次设计交付只校核设计一致性及JSON示例结构，不据此宣称运行能力已经实现。

## v2新增约束

`field_constraints`严格校验占位词、正则表达式和分隔符数组；`responsibility_phrase`要求非空责任属性集合；`responsibility_coverage.unresolved_kind`仅允许review或limitation。意见模板新增`advice_v2`变量，旧版`advice`及不可变历史规则包保留原有措辞。

人员编号通过person_ids逻辑字段读取。仅在一行一个姓名与一个编号时认定身份对应明确；多人多编号未有单独映射时，不猜测排列对应，按姓名重合提示待核实。删除线、合并格、人工意见隔离等原有读取规则继续生效。

## 程序1.2.2的匹配修正

第5条先执行已确认的一对多映射，再核对同主体、同业务、同变体及同措施下同一清单行的部门、岗位组合。组合完全对应时，不因名称属于泛称而重复提出“尚未对应”。具体部门、岗位名称的填报要求仍由`field_constraints`独立执行。不同措施、不同主体以及分属两行的部门和岗位不得拼接为匹配。

第9条用完整短句模式识别“账卡一致”“账实相符”等控制目标；不按关键词包含关系排除整句。真实的“账卡一致核对表”等文书名称继续核对，同句内其他无法解析的引用也继续保留待核实。此次为检查器缺陷修复，未修改冻结规则包及其启停配置。

## 程序1.2.3的岗位职级匹配

第5条在已确认主体、业务、变体、措施及部门范围内，将矩阵单独填写的职级称呼，与岗位名称末尾明确标注同一职级的记录对应。例如“四级职员”可对应“薪酬绩效及体改管理专责（四级职员）”。完全匹配和已确认映射仍优先；不通过任意子串相似或删除全部括号实现匹配。

只有唯一具体岗位名称时自动对应；同一岗位的重复行不构成歧义，不同岗位同职级则列明候选，请填报单位确认。不同职级、跨部门或跨措施记录、带“原”“及以上”等限定的括号内容均不自动对应。冻结规则包仍为1.2.1，具体变更与测试见《岗位职级匹配修复-v1.2.3.md》。

## 规则包1.2.5及责任单位名称检查

后续1.2.5补充第5条，现行规则如下：新增`duties.unit_specificity`独立规则，使用`responsibility_unit_specific`能力及`entity_name_specific`检查点，字段固定为`responsibility`，参数`generic_unit_names`明确列举单位泛称。原`responsibility_coverage`能力新增版本2，参数增加同一泛称列表，用于分开表述单位名称问题与部门岗位差异；版本1行为保留。两个检查可以独立启停，岗位对应成功不豁免单位名称问题，实际候选仍受主体、业务、模板类型、措施和部门范围限制。新规则包要求程序`>=1.2.5,<2.0.0`，旧冻结规则包不修改。具体口径见[责任单位名称检查修复](责任单位名称检查修复-v1.2.5.md)。

## 规则包1.2.4及删除核对能力版本2

R13的`deleted_text_reappears`使用`operator_version: 2`；版本1保留原语义。版本2检查连续删除原文及完整删除的编号条目，允许同措施最终仍保留的原文继续出现在岗位职责。提取条目保留来源范围和父删除片段，不用别名词表替换原文。

以下为1.2.4历史合并机制；1.4.1不执行载体核验，因此不产生待合并载体意见。历史第9条与第13条均独立执行。全部检查完成后，仅对同一行、同一职责原句、同一完整对象进行意见合并：有第13条确定问题时，删除第9条对该对象的漏填提示；多个对象只合并命中者，其他对象重新按本范围的生效模板生成意见。合并记录存入第13条证据，状态计数按最终意见同步更新。第13条停用、范围排除、执行失败或仅待核实时，不据此隐藏第9条问题。新规则包要求程序`>=1.2.4,<2.0.0`，已发布的旧规则包不改写。
